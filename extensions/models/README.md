Model, thinking, and login, as Pi does them: a model button and a thinking-level button in the composer toolbar, a searchable model picker grouped by provider (availability, login status, context window, thinking, price per million tokens), and a login dialog that drives any pi-ai provider's flow, subscription or API key, with credentials shared with pi in `~/.pi/agent/auth.json`.

Picking a model calls `api.configure({ model })`; the server keeps the thinking level when the model supports it and otherwise clamps it with Pi's `clampThinkingLevel`, and the toolbar shows what it configured. A model whose provider is not logged in opens the login for that provider. The thinking menu offers the model's supported levels (Pi's `getSupportedThinkingLevels`), and Shift+Tab cycles them in Pi's order, like Pi. Commands: `model.pick`, `model.thinking`, `model.thinking.cycle` (Shift+Tab), `auth.login`; the status line's model opens the picker through `model.pick`.

A response that ran on another model or thinking level than the response before it gets a quiet divider above it (`model a → b · thinking high → max`), derived from what each stored response records, so it needs no writes, covers branches and older history, and shows where a change took effect rather than when it was picked. Each response records the thinking level its request asked for (`thinkingLevel`, through this repository's Pi Durable patch); responses from before that compare the level the provider reports (`providerThinkingLevel`), which only some providers do. `switches.ts` derives them.

A conversation whose model's provider has no login here (a removed credential, a moved default) switches when its next run's first input is placed (`fallback.ts`, the patched `beforeInput` hook, so typed inputs, deliveries and queued follow-ups alike). Only certain evidence switches: the availability snapshot lacks the login and a fresh `checkAuth` agrees; a pending, failed or timed-out check keeps the model. It switches to the same model id on another provider with a login, else the model its definition runs on (`Profile`, or the label of a branch or lander, through the `models.definition` point that subagents provides), else the first fallback its family names that is usable (`modelFamilies.families.<name>.fallback`), else the configured default (`configuredModel` in `lib/agents.ts`), never to whatever model is first. A family's fallback is one `provider/id` or an ordered list of them, and each move takes the first entry with a login that the mark does not cover, so a conversation can be walked out of a whole chain of spent providers one failure at a time: the second refusal after a move lands on the next entry rather than at the end of the chain. The family's fallback is what lets the chain end somewhere other than the default family's model: with `default` itself on a provider that runs out of quota, the last step would be the very model that just refused. A conversation with no definition (@ultimate, a branch) runs on the `default` family, so that family's fallback covers it; so does one whose definition pins a model of its own. A subscription login (Pi's `isUsingSubscription`; `anthropic` counts as pay-per-token here, since Claude runs on its subscription only through Claude Code) only switches to another subscription, with one exception: the fallback its family names may be a login billed per token, because the owner wrote that step down, so it is no silent switch. Only that step crosses: `same`, `pin` and `default` never move a subscription onto a billed login, and without a family fallback it keeps its model and writes a "needs you" entry once. A crossing move's entry carries `billed: true`, and its card and the line the model reads name the provider as billed per token. It writes one `models.fallback` entry, `{ from, to?, reason: 'same' | 'pin' | 'family' | 'default' | 'quota' | 'none' | 'reset', until? }`, rendered as a card with Pick another (and log in, when a login is what is missing); the model reads one line. A move for quota says so in the reason (`quota`) rather than which step chose the model; a move back to the model its family names says `reset`, and `until` is the moment a refused provider is tried again (see the paragraph below). A run already under way fails once; the watchdog's card then says the provider has no login. New conversations never inherit a model without a login either: branches, standing agents, automation runs and the lander resolve explicit model → usable pin → default, and the root follows the default each time the home opens.

A provider that is logged in but refused a run because the account behind the login is spent — a quota, a usage limit, an empty prepaid balance, a rate limit Pi already retried (`outOfQuota` in `lib/rate-limit.ts`) — is marked instead (`quota.ts`): `models.quota` on the root holds `{ providers: { [provider]: { at, until } } }`, until when the provider may work again. That moment is the reset the refusal names, read out of its text (`resetAt` in `lib/rate-limit.ts`: a timestamp, or a duration like "try again in 3 days" or Pi's own "Try again in ~42 min" when Codex's body carries `resets_at`), or the retry interval when it names none — which is most refusals, and the one this machine gets from Codex, "Codex error: The usage limit has been reached", is one of them. The interval is ten minutes (`RETRY_MINUTES`), and a project raises or lowers it with `quotaRetryMinutes`. The same chain then moves the conversation off it, with `reason: 'quota'` and the entry's card saying so, and a provider the mark covers is never a candidate, so the run does not walk into the same wall. The run that was refused is already lost — one request cannot switch the model under itself — so the watchdog gives it one continuation, and the mark puts that continuation on the fallback: the work finishes there, and a second refusal is reported instead of a third attempt (with a list, the continuation takes the first usable entry, and the next input after that refusal walks on to the following one). Every review after the first one runs on the fallback without an attempt: a new conversation whose model the mark covers moves before its first request. A capacity error (529, overloaded), a billing notice, a 500 or a network error marks nothing.

Only the `review` family comes back by itself (`switchback.ts`). A review conversation's quota move is written down in `models.switchback`, a document on that conversation holding `{ pending: { family: 'review', from, to } }`, and the mark is the only clock: once its moment has passed, that conversation's first input goes back to the model its family names — clamped to that model's thinking levels — and writes a `models.fallback` entry with `reason: 'reset'`. Its move-off entry carries `until`, the moment it goes back, and its card names it; no other family records a move back, and no other family's entry carries a moment, so nothing sweeps another family along with review. A choice the user made meanwhile wins and drops the pending move rather than running it: another model for the conversation, or a family whose model is no longer the one it left, or a provider whose login is gone. The move back is cheap to find — one document read per input — because it names its conversation, and it survives a restart because it is a document.

Login is this extension's own: `server.ts` runs Pi's `modelRuntime.login` behind four actions, `login { provider, type }` → `{ flowId }`, `answer { flowId, value }` (an empty answer is an answer), `cancel { flowId }`, and `logout { provider }`. Each flow is shown in `models.login`, a document on the conversation that started it: status, the pending prompt, and the provider's events, never answers, credentials, or provider error details (a failed flow reads `Login failed`). Flows are process-local; one that dies with its process reads cancelled from the next start on. The dialog streams the document with `useDoc` and renders the events (`auth_url` with open and copy, `device_code` with a countdown, `info`, `progress`) and the `text`, `secret`, `select`, and `manual_code` prompts; closing it or the tab cancels a running flow, as does showing another conversation (the document stays with the one that started the flow), configured providers can log out, and a finished login or logout resets that provider's health to unknown (`extensions/health`) and refreshes the model list with `refreshModels()`, which every tab also calls when its window gains focus, for logins in another tab or in pi.

`picker.tsx` is the model picker (its `ModelRow` also lists models in the conversations extension's Summary model picker), `login.tsx` the login dialog, `state.tsx` the shared helpers (the current model, cycling, dialog ids, which provider the login opens on), `server.ts` the login actions and document.

## Model families

A family is a named role with one model, thinking level, fallback (one model or an ordered list of them) and color: `default` (shown as "Ultimate"), `review`, `fast`, `tiny` and `design` are built in (`lib/families.ts`) and the user can add more. Everything that calls a model runs on a family rather than a model: agent definitions name one (`family: fast`), summaries run on `tiny` and previews on `fast` unless the families' settings assign them elsewhere. Precedence for a definition: a `model` pin in its file, then its `family`, then `default`; an agent's family lives only in its definition, and an overlay naming a family replaces an earlier file's pin. The default family runs new conversations, @ultimate and branches; without a model of its own it follows Pi's default model and thinking, and subagents of the default family inherit their parent's model. A `summaryModel` or `instance.model` setting pins its feature to one model; moving the feature to a family removes that user-settings pin.

The subagents extension's **Agents** panel is the one place to configure them (⌘K **Model families…** and the picker's row open it). Each family heads a group, its model and thinking on one line; clicking it opens the family's popover (`family-editor.tsx`): model, thinking, the ordered fallback, color, and **Remove** for a family the user added. **+ Family** adds one. Under each family sit the agent definitions and features that run on it, and last those that pin a model of their own. An agent row opens its definition; its **move** menu runs it on another family by saving its definition, which for a built-in writes an overlay holding only `family`. A feature's menu saves its assignment with the families; one the project's settings decide is fixed. A family change applies to conversations started after it; open ones keep their model. The definition form shows the family it runs on and links to the panel, or pins a model of its own.

A family's `fallback` is where its conversations move when their model's provider has no login here or runs out of quota (see the fallback paragraph above): a `provider/id`, or an ordered list of them that each following failure walks one step further (`familyFallbacks` in `lib/families.ts` returns the list, and `fallback.ts` takes the first entry that is usable). It is saved and shown in the family's popover and settable as a team in the project's settings. It is the one step of the chain that may cross from a subscription login to a provider billed per token, since it is the owner saying where to spend instead, and that holds for any entry of a list, not only its first. The entry then carries `billed: true` and its card says so. Every entry is a model, never another family, so a chain cannot point back at itself. Parsing refuses, naming the field, an entry that is not a `provider/id` string (including a family name), an empty list, a list that names one entry twice, and any entry equal to the family's own `model`, which could never fire: a list that silently dropped a typo would move a conversation somewhere nobody wrote. The family's popover lists the entries in order, each with a remove button and a **Add another model** picker under them, and keeps the shape it was saved in: a one-step fallback stays a string unless a second entry is added.

Families are kept per project in `~/.ultimate/model-families.json`, keyed like the project's trust decision (a linked worktree shares its main checkout's), and each save is also the `recent` entry that every project without its own starts from (`lib/families-settings.ts`). A project's `.ultimate/settings.json` `modelFamilies` (`{ families, assign }`) applies over them for a team; the family's popover says when it changes a family, and a feature it assigns cannot be moved there. `assign` holds features only (`summaries`, `preview`).

Families show with their color only where they are configured: the Agents panel and the definition form (`families.tsx`: `useFamilies`, `FamilyDot`, `FamilyLabel`, exported through `ui.tsx`). Elsewhere a model shows by its id. The browser fetches the families once, again on window focus and after a save.
